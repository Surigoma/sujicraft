# UIデザインレビュー

UIのデザイン案・スクリーンショット・実装済み画面のレビューを求められた際、またはUI変更のデザインを確認する際に使用する。

## 目標と姿勢

利用者が情報を理解し、目的の操作を迷わず完了できるかを確認する。

ユーザーが指定した要件・ブランド・既存のデザインシステムを基準にする。個人の美的な好みで置き換えたり、依頼されていない全面的な再設計を提案したりしない。

[共通原則](../../shared/principles.md)に従い、確認した事実と仮定を区別する。レビューでは指摘と修正案を示し、画面やコードの修正は依頼された場合に行う。

## レビュー前

- 対象の画面、利用者、目的の操作、要件、対象端末を確認する。既存資料から分かることは先に調べる。
- 指定された参考デザイン、デザインシステム、関連画面を確認する。
- 実装済みUIは、実際の画面を表示し、操作して検証することを必須とする。ソースコードやスクリーンショットだけで実画面検証を完了したとしない。
- デザイン案やスクリーンショットしかない場合は、操作・状態変化・支援技術での利用などを未確認として扱う。

## 実画面での検証

対象アプリをブラウザーや実行環境で表示し、対象端末・画面サイズで主要なユーザーフローを操作する。表示崩れ、視覚的な強弱、操作結果、該当する読み込み・空・エラー状態、キーボード操作とフォーカスを確認する。対象に関係する状態と条件を選び、確認結果を記録する。

実装や実行環境がない場合、起動できない場合、アクセスできない場合は、理由と不足している条件を示し、実画面検証は未完了と報告する。デザイン案やスクリーンショットの範囲でレビューは行えるが、実装済みUIの検証完了とは区別する。

検証でデータ削除・購入・送信など外部への影響が生じる操作は、許可された範囲とテスト環境・テストデータで行う。実行できない操作は未確認として記録する。

## レビュー観点

### 1. 情報と操作の理解しやすさ

- 画面の目的、重要な情報、主要な操作が分かるか。
- 情報の階層・グループ分け・配置が、利用者の理解と操作の順序に合っているか。
- 配置・余白・文字の強弱・色などによって、重要な情報から主要な操作へ自然に視線が誘導されるか。複数の強調が競合したり、読む順序と操作順序が食い違ったりしていないか。
- ラベル・説明・ボタンの文言から、操作と結果を予測できるか。
- 誤操作しやすい配置や、破壊的な操作を取り違える表現がないか。

### 2. 視覚的な一貫性と読みやすさ

- 余白・整列・文字・色・アイコン・コンポーネントが、既存のデザインルールと整合しているか。
- 文字の大きさ、行間、情報量、強弱が読み取りやすいか。
- 装飾や強調が重要な情報・操作を埋もれさせていないか。

### 3. ユーザーフローと状態の伝わり方

- ナビゲーション、入力、選択、主要な操作を迷わず行えるか。
- ユーザーフローは、利用者が目的の操作を始めてから完了するまでの経路として確認する。画面遷移・クリック・入力・選択・確認の手順をなるべく少なくできているか。不要な往復、重複入力、不要な選択や確認を減らせないか。
- 手順を減らすために、必要な情報・理解・誤操作防止を損なっていないか。破壊的な操作などに必要な確認は維持する。
- 読み込み中・データなし・エラー・成功・操作無効など、該当する状態が伝わるか。
- 入力エラーの理由と修正方法が分かり、失敗から回復できるか。
- 操作結果のフィードバックがあり、連続操作や誤操作による混乱を防げるか。

### 4. 画面サイズと内容への適応

- 対象の画面サイズで、重なり・切れ・意図しないスクロールがないか。
- 長い文字列、情報量の増減、文字の拡大でも、情報と操作を利用できるか。
- 該当するタッチ操作で、操作対象の大きさと間隔が適切か。

### 5. アクセシビリティ

- 文字と背景のコントラストが十分か。色だけに意味を依存していないか。
- キーボードで操作でき、フォーカスの位置と順序が分かるか。
- 入力欄や操作要素に適切なラベルがあり、支援技術でも意味と状態が伝わるか。
- 動きや点滅が利用を妨げないか。

適合する規格や数値基準を断定する場合は、該当する公式資料と実測結果を確認する。見た目だけでアクセシビリティへの適合を宣言しない。

## 報告

重要な問題から順に、次を示す。

- 重要度：修正必須・修正推奨・任意
- 対象の画面・要素・状態・確認条件
- 観察した問題と利用者への影響
- 根拠となる画面や再現手順（視線の動きなど、観察・測定していないものは仮説として示す）
- 既存のデザインに適合する最小限の修正案

操作の完了を妨げる問題や重大な誤操作・アクセシビリティの問題を優先する。好みの違いは任意とし、要件違反や利用上の問題と区別する。

最後に、確認した画面・状態・端末条件と、未確認の範囲を簡潔に示す。実質的な問題がなければ、そのことを明確に伝える。
