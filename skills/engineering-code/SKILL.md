# コーディング

本番コード・テスト・設定・マイグレーション・スクリプト・インフラ定義を変更または生成する際に使用する。

[共通原則](../../shared/principles.md)を確認し、作業に適用する。

## 目標

既存コードベースに適合し、確実に検証できる、最小限かつ整合性のある差分で要件を実装する。

## 編集前

- 関連するコードと周辺のテストを読む。
- 変更する処理がどう呼ばれ、何に影響するかを追う。
- 新しく作る前に、既存のユーティリティ・パターン・抽象化を探す。
- リポジトリの指示と、その箇所の慣習を確認する。
- [共通原則のリスク基準](../../shared/principles.md#リスクのある変更の基準)に該当する場合は、実装前に影響範囲・失敗条件・復旧方法・検証方法を明らかにする。

## 実装ルール

### 変更範囲を限定する

正しさのために必要でない限り、無関係な整理・名前変更・大量の整形・依存関係の更新・リファクタリングを避ける。

### 新しく作る前に再利用する

基本は次の順に検討する。保守性・可読性を改善できる場合のライブラリ選択は、次節に従う。

1. 既存プロジェクトのコード
2. 言語・プラットフォームの標準機能
3. 導入済みの依存関係
4. 小規模なローカル実装
5. 具体的な理由がある場合のみ、新しい依存関係や抽象化

### 保守性・可読性を改善するライブラリを選ぶ

標準的な関数や機能が存在していても、ライブラリの利用によって保守性・可読性が改善する場合は、ライブラリを採用候補とする。単にコードが短くなるかではなく、意図の理解しやすさと変更・保守のしやすさで比較する。

新規ライブラリの導入だけでなく、既存ライブラリを新しい用途へ使う場合も、調査と採用の確認を必要とする。承認済み用途での通常利用は、採用の確認を繰り返さない。用途は、ライブラリが担う役割と適用する処理・機能で判断する。

採用前に、公式リポジトリ・リリース履歴・変更履歴・移行ガイドなどの一次情報を調査する。

- 現在もメンテナンスされているか。リリースや修正の状況、課題への対応、サポート方針を確認する。更新頻度だけで判断しない。
- 過去に大きな変更や破壊的変更を何度も繰り返していないか。頻度・内容・互換性への配慮・移行負担を確認する。
- 今回の用途で得られる改善が、依存関係の追加や将来の更新・移行の負担に見合うか。

標準機能での実装との比較、採用候補とバージョン、調査の根拠となる参照先、利点・リスク・未確認事項を示し、ユーザーに採用の確認を取る。確認を得るまでは、依存関係の追加や採用を前提とした実装を行わない。

### ライブラリの導入・更新とセキュリティ

新規ライブラリの導入と通常のバージョン更新は、採用するバージョンの公開から最低3日（72時間）待ち、不具合報告・セキュリティ情報・変更履歴を確認して採否を判断する。公開日時を確認できない場合は、待機期間を満たしたと断定しない。期間を過ぎても、調査・検証に未解決の懸念があれば導入しない。

- 採用するバージョンについて、更新の場合は現在のバージョンについても、公式のセキュリティ情報や脆弱性情報を調べ、今回の利用方法への影響を確認する。
- 破壊的変更・移行作業・サポート条件の変更を伴う更新は、待機日数にかかわらず、影響・移行方法・復旧方法を示して更新前にユーザーへ確認する。メジャー・マイナーなどの番号だけで判断しない。
- 互換性を保ち、承認済み用途を変えない通常更新は、依頼された作業の範囲内で、上記の調査と必要なテストを行って進める。無関係な更新は行わない。
- 悪用が確認されている脆弱性など、緊急対応の根拠があるセキュリティ対応の導入・更新は、3日待機の例外とする。現在の脆弱性によるリスクと更新リスクを比較し、更新または暫定対策を選ぶ。待機の例外でも、調査・検証や必要なユーザー確認は省略しない。
- 更新を見送る場合は、理由・必要な暫定対策・再確認の時期を示す。

3日はこのスキルの通常の導入・更新の基準であり、安全性を保証する期間ではない。運用例は [Dependabotの公式資料](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates)を参照する。

### 重要な保護を維持する

次を犠牲にしない。

- 信頼境界での入力検証
- 認可・セキュリティ
- 安全な動作に必要なエラー処理
- データの整合性
- 可観測性
- 該当する場合のアクセシビリティ
- 互換性の要件
- 運用上の変更を元に戻せること

### 将来を推測した抽象化を避ける

将来役に立つかもしれないという理由だけで、ファクトリー・インターフェース・汎用フレームワーク・設定可能な層・ヘルパーの階層を導入しない。

現時点のコードに具体的な重複・境界・テスト上の必要性・ドメイン概念があり、切り出す利点がある場合にだけ抽出する。

### 責任分離・テスト・可読性・フォルダー構成

- 異なる責任を同じ実装単位に混在させず、設計した責任の境界を保つ。
- 設計時に考えたテストを実装できるよう、必要な依存や副作用の境界を保つ。テストでは実装の内部構造をなぞるだけでなく、期待する動作を検証する。
- 人間が意図と正常時・失敗時の動作を読み取れる命名・制御の流れにする。読みやすさやデバッグのしやすさを犠牲にしてコードを短くしない。
- 追加・変更する実装ファイルは責任に対応したフォルダーへ配置し、平置きを避ける。テストも対象との対応が分かる場所に置く。
- 既存の責任別構成を再利用し、無関係な移動や不要な階層追加は行わない。既存構成の整理が必要な場合は、理由・範囲・影響を示してユーザーへ確認してから行う。

## 検証

編集後は、次を行う。

動作変更では、変更後の期待動作を検証する新規または既存の自動テストを実行する。既存テストで不足する場合は追加・更新する。テストが失敗した場合、または実行できない場合は、検証未完了として結果・理由を報告し、完了扱いにしない。

1. 最終的な差分を確認する。
2. 関連する最も狭い範囲のチェックから実行する。
3. 実施可能で適切な場合は、リポジトリ全体などの広い範囲のチェックを実行する。
4. 変更した境界でのエラー・失敗時の動作を検証する。
5. 意図しない破壊的変更や無関係な変更がないことを確認する。

実際に実行していないテストを、成功したと報告しない。実行したチェックと結果、実行できなかったチェックと理由を区別して報告する。

## 完了報告

次を要約する。

- 何を変更したか
- なぜこの実装を選んだか
- 何を検証したか
- 未検証の仮定や残っているリスク
